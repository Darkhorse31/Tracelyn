# Tracelyn Phase 1 — Build Plan

Source of truth: docs/specs/2026-10-23-serverlens-design.md
All code is written by Cursor CLI. Each step ends with: builds cleanly (`npm run tauri build` debug or `cargo check` + `npm run build`), tests pass, a short summary in docs/progress.md, and a git commit. COn reviews after each step before the next one starts.

## Step 1 — Shell, design system, server management, SSH connect
- Scaffold Tauri 2 + React + TypeScript (Vite), Tailwind, shadcn/ui, Lucide, Inter + JetBrains Mono.
- Implement design tokens from spec section 7a (colors, spacing, typography, dark theme) and the app layout: sidebar with server switcher, top bar with time range picker (placeholder), main content area.
- Server management UI: add/edit/remove server (name, host, port, user, auth type key or password, key path, optional passphrase, labels).
- Rust: server config store (no secrets), secrets in Windows Credential Manager (keyring crate), SSH connection via russh with key and password auth, host key TOFU check, "Test connection" command returning OS info.
- Overview page skeleton showing server cards with connection status.
- Done when: a real server can be added and connected with key or password, and status shows on its card.

## Step 2 — System collector, Overview and Server views
- ConnectionManager with keepalive and exponential backoff reconnect.
- System collector (/proc stat/meminfo/loadavg/net/dev/diskstats, df, ps, ss -s, systemctl for detected services) at spec intervals; Rust unit tests with fixture files.
- Event streaming to UI, batched to ≤4 updates/s per view; hidden views unsubscribe.
- Overview cards with sparklines; Server view with live charts, top processes, services.

## Step 3 — Web server detection, log streaming, Web traffic view
- Detect nginx/apache, read config to find log paths and log_format; parsers for common/combined/custom with fixture tests.
- tail -F stream over SSH channel; Web traffic view (req/s, status breakdown, top URLs/IPs, bandwidth, virtualized live log with filters).
- Permission-denied and missing-timing notices per spec.

## Step 4 — API endpoints (APM-style) view
- Route normalization (ids, uuids, hashes → :id) + manual rules; per-endpoint throughput, avg/p50/p95/p99, error rate, status breakdown, charts, latency heatmap; slowest/most-failing tables; click-through to logs.

## Step 5 — Redis view
- redis-cli INFO / SLOWLOG / keyspace collector, auth via Credential Manager; Redis view per spec.

## Step 6 — Storage and history
- SQLite store, raw 7d + 1-min rollups 90d, configurable; time range picker wired to all views.

## Step 7 — Alerts
- Rule engine with spec defaults, Windows notifications, alert history and rule editor.
